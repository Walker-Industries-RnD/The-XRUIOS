8 - Building a XRUIOS App

Building a XRUIOS App

An "app" on XRUIOS is anything that holds a stable id and its own app password (PSK) and talks to the Manager broker over the Eclipse channel. It never touches a worker, a file, or a key directly: it asks the broker for a capability by name, and the broker either runs it in the owning worker or refuses it. That contract is identical whether your app is a console tool, a desktop window, a game-engine shell, or a mod inside a game engine. Only the shell around the client changes.

This page is a set of complete examples, smallest first. Each one comes with the manifest that grants it what it needs. The projects behind them are on 3 - A CMD App, 4 - A Desktop App and 5 - An Aether Mod.

The one contract every app shares

your app  ──(app id + app password)──►  Manager broker
                                        │  post-quantum handshake (Kyber + AES-256-GCM)
                                        │  XRUIOS.Permission check on the capability name
                                        ▼
                                   owning worker runs it, result comes back

An app needs three things, and it invents none of them:

  1. An id the Manager gives it. It is always app:<name>, where <name> is the name in the app's manifest.
  2. Its password (PSK). The Manager makes a new one for every app each time it starts, and keeps it in memory.
  3. The broker address, the loopback port the Manager is listening on.

The Manager hands these over in one of three ways, and the app uses the first that is available:

Way How it works
Environment The Manager started the app (spawn) and put XRUIOS_APP_ID, XRUIOS_APP_PSK and XRUIOS_BROKER_ADDR in its environment.
Creds file The Manager runs with --dev-creds and wrote %LocalAppData%\XRUIOS\Public\<name>.creds. For development only.
Enrollment The app starts on its own and asks the running Manager over a local pipe. The Manager looks at which process is asking, checks it runs from the registered path and that its folder still matches the approved baseline, and only then answers.

So an app cannot choose where to connect, cannot invent a password, and cannot pretend to be another app. A copy of the executable on another machine, or in another folder, gets nothing.

A helper for the console examples

The console examples all start the same way. This small file finds the credentials and connects. (It is the same ladder WorkerBroker uses in the desktop apps, without the creds file.)

using XRUIOS.Interfaces;

public static class Xruios
{
    public static async Task<AppProvisioning> CredentialsAsync(string appName)
    {
        string? id   = Environment.GetEnvironmentVariable("XRUIOS_APP_ID");
        string? psk  = Environment.GetEnvironmentVariable("XRUIOS_APP_PSK");
        string? addr = Environment.GetEnvironmentVariable("XRUIOS_BROKER_ADDR");
        if (id != null && psk != null && addr != null)
            return new AppProvisioning { AppId = id, PskBase64 = psk, BrokerAddress = addr };

        // Throws "No XRUIOS.Manager is running to enroll with." if there is no unlocked Manager.
        return await XruiosEnrollment.EnrollAsync(appName);
    }

    public static Task<EclipseSecureClient> ConnectAsync(AppProvisioning p, string clientName) =>
        EclipseSecureClient.ConnectAsync(p.BrokerAddress, clientName, p.Psk, identity: p.AppId);
}

The .csproj for every console example is the one on 3 - A CMD App: a net10.0 exe that references XRUIOS.SecureLayer and EclipseProject.dll.

Example 1: Agenda (read and add events)

The smallest useful app. It reads today's events and adds one.

var cred = await Xruios.CredentialsAsync("agenda");
await using var mgr = await Xruios.ConnectAsync(cred, "agenda");

string today = DateTime.Today.ToString("yyyy-MM-dd");

string uid = await mgr.InvokeAsync<string>("AddEvent",
    new() { ["day"] = today, ["summary"] = "Stand-up" });
Console.WriteLine($"added {uid}");

string events = await mgr.InvokeAsync<string>("GetEvents", new() { ["day"] = today });
foreach (var row in events.Split(';', StringSplitOptions.RemoveEmptyEntries))
    Console.WriteLine(row.Trim());

Its manifest, agenda.json:

{
  "name": "agenda",
  "exe": "C:\\Tools\\Agenda\\Agenda.exe",
  "capabilities": [ "GetEvents", "AddEvent" ],
  "events": []
}

XRUIOS.Manager install-app agenda.json
XRUIOS.Manager stop
XRUIOS.Manager start

Each row GetEvents returns is the start time and the summary, for example 09:00 Stand-up. An event with no time of day shows 00:00.

GetEvents and AddEvent also take an optional calendarId. Call ListCalendars (add it to capabilities) to find the ids; it returns id|name|color;....

Example 2: Lap timer (several capabilities, ids and parsing)

Capabilities return plain text, so an app parses it. This one reads the clock and runs a stopwatch with laps.

var cred = await Xruios.CredentialsAsync("laptimer");
await using var mgr = await Xruios.ConnectAsync(cred, "laptimer");

// "shortTime|shortDate|longTime|longDate|zone|iso"
var now = (await mgr.InvokeAsync<string>("Now", new() { ["tz"] = "" })).Split('|');
Console.WriteLine($"{now[0]} on {now[1]} ({now[4]})");

string id = await mgr.InvokeAsync<string>("StopwatchStart");   // returns the stopwatch id
Console.WriteLine("Press Enter for a lap, q then Enter to stop.");
while (Console.ReadLine() != "q")
{
    // "lapNumber|secondsElapsed"
    var lap = (await mgr.InvokeAsync<string>("StopwatchLap", new() { ["id"] = id })).Split('|');
    Console.WriteLine($"lap {lap[0]} at {lap[1]} s");
}

// "hh:mm:ss.fff;1|12;2|30": the final time, then each lap
var parts = (await mgr.InvokeAsync<string>("StopwatchStop", new() { ["id"] = id })).Split(';');
Console.WriteLine($"total {parts[0]}");

{
  "name": "laptimer",
  "exe": "C:\\Tools\\LapTimer\\LapTimer.exe",
  "capabilities": [ "Now", "StopwatchStart", "StopwatchLap", "StopwatchStop" ],
  "events": []
}

If the app calls StopwatchElapsed it must be added to the list too. Asking for a stopwatch id that does not exist comes back as an ordinary failed call carrying the worker's own message ("A Stopwatch with this ID does not exist."), so catch it and show it.

Example 3: Alarm watcher (events instead of polling)

An app that reacts when something happens does not poll. It opens an event stream. The stream keeps its own session, reconnects by itself, and picks up from where it left off after a blip.

using XRUIOS.Interfaces;
using XRUIOS.Interpreter;

var cred = await Xruios.CredentialsAsync("alarmwatch");

await using var stream = XruiosEventStream.Start(cred.BrokerAddress, cred.AppId, cred.Psk,
    e =>
    {
        if (e.Name != XruiosEventNames.AlarmFired) return;
        var alarm = EventJson.Read<AlarmInfo>(e.Payload);
        Console.WriteLine($"ALARM '{alarm.Name}' at {alarm.Time}");
    },
    onError: ex => Console.Error.WriteLine(ex.Message));

Console.WriteLine("Watching. Press Enter to quit.");
Console.ReadLine();

{
  "name": "alarmwatch",
  "exe": "C:\\Tools\\AlarmWatch\\AlarmWatch.exe",
  "capabilities": [],
  "events": [ "AlarmFired" ]
}

An event is delivered only if the app holds Events.<Name>. The manifest's events list is turned into those grants. An app with an empty list connects fine and simply never sees anything. A handler that throws is reported through onError and does not stop the stream.

Example 4: A window

A desktop app is Example 1 with a window on top. The apps that ship use OpenSilver in a Photino window, and a page is as short as this:

Loaded += async (_, _) =>
{
    await AppShell.InitializeAsync("XRUIOS.App.Time");
    ActiveCountLine.Text = await TimeSource.NowAsync();
};

TimeSource.NowAsync() is a hole: a one-file wrapper around the Now capability. The whole walkthrough, including a WPF version, is on 4 - A Desktop App.

Example 5: Your own assistant (a provider app)

PocketPal, the assistant, does not choose a model. Any app can provide the answers. When an app calls Ask, the Assistant worker stores the question, announces AssistantAsked, and waits (up to 15 seconds by default) for a provider to call AnswerAssistant. With no provider, the question stays pending and shows unanswered in the history.

You write the brain; AssistantProvider handles the plumbing.

using XRUIOS.Apps.Shared;
using XRUIOS.Interpreter;

public sealed class EchoBrain : IAssistantInterpreter
{
    // Replace with a local model, a remote API, a rules engine...
    public Task<string> AskAsync(string prompt, CancellationToken ct) =>
        Task.FromResult($"You asked: {prompt}");
}

await AppShell.InitializeAsync("mybrain");
await using var pal = await AssistantProvider.StartAsync(
    AppShell.Broker, new EchoBrain(), ex => Console.Error.WriteLine(ex.Message));
Console.ReadLine();

{
  "name": "mybrain",
  "exe": "C:\\Tools\\MyBrain\\MyBrain.exe",
  "capabilities": [ "AnswerAssistant", "PendingQuestions" ],
  "events": [ "AssistantAsked" ]
}

Questions are answered one at a time. Questions asked while no provider was running are fetched with PendingQuestions when the provider starts. AssistantProvider is in XRUIOS.Apps.Shared, so a provider references that project, as the UI apps do. The app that asked also learns of a late answer through the AssistantAnswered event.

Example 6: A game-engine shell (Aether Engine and Godot)

An engine can be the XRUIOS shell. It connects as a normal app, receives the events it was granted, and draws things itself instead of the desktop doing it. Reference XRUIOS.Aether (it targets net8.0 for Godot), then:

using XRUIOS.Aether;
using XRUIOS.Interpreter;

public partial class XruiosBridge : Node
{
    private AetherShell? _shell;

    public override async void _Ready()
    {
        // Your own presenter for notifications (an in-world panel, say).
        XruiosInterpreter.Use<INotificationInterpreter>(new WorldPanelNotifier(this));

        _shell = await AetherShell.ConnectAsync(
            "MyAetherShell",
            post: a => Callable.From(a).CallDeferred(),   // Godot's scene tree is main-thread only
            onError: ex => GD.PrintErr(ex.Message));

        GD.Print(await _shell.InvokeAsync<string>("Now"));
    }

    public override void _ExitTree() => _ = _shell?.DisposeAsync();
}

public sealed class WorldPanelNotifier : INotificationInterpreter
{
    private readonly Node _host;
    public WorldPanelNotifier(Node host) => _host = host;
    public void Show(string title, string body, string? source = null) { /* spawn a panel */ }
}

{
  "name": "MyAetherShell",
  "exe": "C:\\Games\\MyShell\\MyShell.exe",
  "capabilities": [ "Now" ],
  "events": [ "ShellNotify", "ShellAppearance", "ShellLaunch", "NotificationPosted" ]
}

Two more things make this work:

  • Start the Manager with XRUIOS_SHELL=aether in its environment. The workers it launches inherit it, and from then on the visual parts of a worker (toasts, dark mode and wallpaper, opening a scene) are sent to the engine as ShellNotify, ShellAppearance and ShellLaunch events instead of being done on the desktop. The rest (audio, power, clipboard) stays on the OS. App ids that start with aether: are scenes.
  • The engine's exe in the manifest is the engine executable. It enrolls like any other app, so its folder is approved with install-app first.

AetherShell hands each event to the interpreter you registered for it. Events no interpreter handled arrive on its Unhandled event. More in 15 - XRUIOS.Aether and Apps.Shared and 13 - XRUIOS.Interpreter.

Example 7: Changing and removing an app

Edit the manifest and install it again. The grants follow the file, and a capability you removed is revoked the next time the Manager starts.

XRUIOS.Manager apps                        # every app, its exe, capabilities and events
XRUIOS.Manager install-app agenda.json     # add or change
XRUIOS.Manager uninstall-app agenda        # remove, revoke its grants, forget its approval

Rebuilding the app changes its files, so approve it again: XRUIOS.Manager baseline agenda. Until you do, enrollment is refused with "app failed integrity check".

Example 8: A mod inside a game engine

A mod is an app that runs inside a host (a HangarBay / Aether game or scene) instead of as its own process, so it can't even open a socket to the broker: CasCore made System.Net uncallable. Instead the host holds the permission authority and the mod asks the host. The permission story is the same - one XRUIOS.Permission authority, capabilities by name - but the plumbing is the mod registry, not EclipseSecureClient. Full detail in 6 - Aether Engine Integration; here is the build.

A note on names: the mod registry and its test (XRUIOS.AetherModTest) use their own capability strings, such as Time.Calendar:GetEvents, in the host's permission store. Those belong to the host's policy. The Manager's broker, used by every other example on this page, uses the plain names from 5 - Permission Catalog.

On the host side (the game integrating XRUIOS - written once, not by the mod author):

// one registry over the host's real XRUIOS.Permissions handler + context
var mods = new ModRegistry(handler, appContext, privateRoot, memoTtl: TimeSpan.FromSeconds(5));

// enroll the mod by its Notary-verified package id -> host-assigned ModId
var widget = mods.Enroll("com.hollvania.calendarwidget");

// grant it exactly what it may do - persisted in XRUIOS.Permissions under its ModId
await mods.GrantAsync(widget, "Time.Calendar:GetEvents");
// note: no AddEvent, no DeleteEvent granted

// give it a jailed filesystem: its own private dir, plus any named roots it's granted
var fs = mods.CreateFileSystem(widget, grantableRoots);

On the mod side, the author writes against what the host hands in - never against System.IO, System.Net, or the broker. Two real doors exist today (both are in the Hangarbay engine, not made up here):

using Walker.Content.Contracts;
using Walker.Content.Security;

// A scene mod: the host calls these, the mod never runs its own loop.
public class CalendarWidget : IHostedScene
{
    private IHostServices _host;

    public void OnLaunch(IHostServices host) { _host = host; host.Log("widget up: " + host.PackageId); }
    public void Tick(double delta) { /* draw, using host.Resources for textures and audio */ }
    public void OnSuspend() { }
    public void OnResume() { }
    public void OnShutdown() { }
}

// Files go through the jailed file system the host builds for this mod.
public string SaveNote(SandboxFileSystem fs)
{
    fs.WriteAllText("notes/ok.txt", "hello from mod");   // needs fs.write
    return fs.ReadAllText("notes/ok.txt");               // needs fs.read
}

IHostServices offers the package id, the resource catalog, spawning models, signals and logging. It does not offer XRUIOS capabilities such as the calendar. To give a mod one, the host writes a small service of its own: it holds a normal app connection (Example 6), and before every call it asks registry.IsAllowed(mod, "Time.Calendar:GetEvents") and only then calls the broker. That bridge is not shipped yet. Anything the mod tries outside these doors (File, Process, sockets) is blocked by CasCore whatever it was granted.

The mod author's mental model is the same contract, minus the connection: ask the host for something, get a result or a refusal. What changes is that identity is host-assigned (ModId from the Notary package id, so a mod can't claim to be another), grants are persisted per ModId, sensors and files are themselves capabilities, and an unsigned mod (EnrollEphemeral) can't bank trust across sessions. The runtime proof is in 6 - Aether Engine Integration.

Shared pieces (all of the above)

Initialization

A worker owns its store and sets it up itself on first launch; the Manager does not reach into a worker's data. By the time the broker routes your first AddEvent, the Calendar worker has already created its Calendar directory. An app should never have to initialize a worker it cannot even see. When you add a worker, put its setup in its own Program.cs (see 2 - A Worker).

Capability names are the whole API

Your app's surface is the set of names it was granted. Design the app around the names you will call, then list exactly those in the manifest. The full list is in 5 - Permission Catalog. Anything else is denied by construction.

Failure is a first-class state

What you see What it means What the app should do
No XRUIOS.Manager is running to enroll with. The Manager is stopped or locked (a locked Manager opens no enrollment pipe) Say "XRUIOS is locked, log in first". Do not retry in a loop.
Manager refused enrollment: no such registered app The name is not in the Manager's list Check the manifest name and run XRUIOS.Manager apps.
...caller is not the registered app (path mismatch) The program runs from a different folder than the one registered Run it from the registered exe path, or reinstall the manifest.
...app failed integrity check The app's folder changed since it was approved Run XRUIOS.Manager baseline <name>.
A handshake that fails without a clear message (the broker's own text is "Connection refused: unknown client identity", and some clients only show a generic gRPC handler error) The app id or password is not one the Manager issued this run Restart the app so it enrolls again. Passwords change every time the Manager starts.
XRUIOS.Permission denied '<name>' for app:<app>. The app was not granted that capability Do not offer the action. If it is needed, add it to the manifest.
No worker exposes '<name>'. Granted, but the worker is not running (not approved, crashed, not built) Check the Manager's log; run baseline for that worker.
Any other failed call The call ran in the worker and the worker reported an error Show the worker's message. It is a real error, not a permission one.

A denial and a handshake failure are the security model doing its job. Treat them as expected states, not exceptions to bury.

The password never lives in your binary

Console, desktop, engine shell or mod: your app is not trusted with a secret it can leak. The Manager makes the password fresh on every start, gives it only to the process that passed its checks, and keeps it in memory. The mod never has one at all, because its host connects. This is what makes "just send me the exe" safe.

Proven at Runtime

The permission model isn't just designed - it's been run end to end and attacked. This page is the evidence, in two parts: the original runs from when the model was first built, and the runs after the hardening work (signed baselines, the audit trail, the app registry).

The full round-trip

XRUIOS.Manager login demo <pw>     # Argon2id wraps the master key; DPAPI seals it to the OS session
XRUIOS.Manager baseline            # sign the file tree of every built worker and app
XRUIOS.Manager run --dev-creds     # unseals, launches the workers, broker up
XRUIOS.Diagnostics                 # connects as an app and probes everything
  • Login created the user, wrote the public login file and the DPAPI seal. run unsealed the master key with no password prompt.
  • 28 of 28 workers launched, in batches of 3 (Launching 28 workers, 3 at a time...). Each announced its own loopback port, its own Kyber public key and its own capability list.
  • The app completed the post-quantum handshake (Kyber + AES-256-GCM): SECURE.
  • The diagnostics harness reported 33 passed, 0 warnings, 0 failed across 33 probes: the handshake, a ping for each of the 28 workers, a Calendar add-then-read round-trip, and the two refusal checks.
  • DeleteEvent (not granted) was refused: XRUIOS.Permission denied 'DeleteEvent' for app:diagnostics.
  • A throwaway test harness (not part of the repo) ran 36 further checks over Calendar, Chrono, Stopwatch, MediaAlbum, Assistant, enrollment, events and alarms. All 36 passed.
  • The console examples on 8 - Building a XRUIOS App (Agenda, Lap timer, Alarm watcher) were run against the live Manager with the credentials of built-in apps. The add and read worked, the delete was refused, the stopwatch laps parsed as documented, and the alarm event arrived. The assistant provider example was compiled but not run, and the Aether example was not built.

Every wall in 1 - The Model fired for real: process isolation (28 separate exes), password isolation (a PSK per worker), key isolation (an HKDF key per worker), and the permission check on the privileged call.

The pentest - the original four attacks

Attack Result
Forged app identity + random password (app:hacker, bogus PSK) hitting the broker No secure channel - the handshake failed because the PSK resolver returns null for an unknown id
Direct-to-worker bypass (skip the Manager, connect straight to the Calendar worker's port) Refused - the worker only completes a handshake with the Manager's PSK, which the attacker doesn't hold
Ungranted capability (DeleteEvent from an app granted only read/add) Denied by XRUIOS.Permission before it reached the worker
Tampered binary (a worker's exe modified after approval) Notary refused to launch it: FAILED checksum: 2 modified

That last row happens for real whenever a worker is rebuilt. The Manager compares the folder against the tree it signed, sees the files changed, and refuses to launch it until XRUIOS.Manager baseline is run again. The anti-tamper works because it catches a legitimate change it was not told about.

After the hardening work

Audit tampering

Each worker and the Manager keep a chained log (see 9 - XRUIOS.SecureLayer). Two edits to a real worker log were tried, followed by XRUIOS.Manager audit:

Edit Result
One field changed in entry 3 ("Ok":true to "Ok":false) BROKEN XRUIOS.Worker.Stopwatch at entry 3: entry was modified (MAC mismatch)
The last two lines deleted, with no anchor recorded yet OK XRUIOS.Worker.Stopwatch 8 entries. The chain alone cannot see lines removed from the end.
The last line of the Calendar log deleted, after the Manager had anchored it BROKEN XRUIOS.Worker.Calendar entry 22 that the Manager anchored is gone (log cut short or replaced)

The second row is why the Manager records each worker log's newest entry in its own log every 5 minutes and at shutdown. A cut-off tail is only caught for entries recorded before the cut. The most recent entries, since the last anchor, are not covered until the next one.

Bugs that were fixed

Found when Cause Fix
Handshakes under parallel load Pariah's Kyber and Dilithium calls are not safe from several threads at once, so two sides derived different keys PqcGate serializes the crypto step
Parallel worker launch The Manager read a worker's announcement file while the worker was writing it The SecureStore retries on a sharing violation
Every worker exited with code 44 after signed baselines were added The tree was keyed by absolute path, and the same folder can be spelled differently by two processes Trees are compared with paths relative to the folder (BaselineSeal.Relativize)
A failed call in a worker showed up in the app as "Exception was thrown by handler" The broker rethrew the worker's exception The broker returns it as a normal failed response with the worker's own message
A call after a long idle failed The worker had dropped the idle session The server answers with the Unauthenticated status and the client handshakes again and retries once
The Calendar worker could not create events Hangfire (used for scheduling) had no job storage configured The worker sets in-memory storage at startup
GetEvents returned nothing right after AddEvent An event's time zone was read as UTC when converting to local time The calendar converts through the event's own time zone
The harness reported 32 probes for 28 workers The harness's own worker list was missing Assistant, so it pinged 27 Assistant added to the list (now 33 probes)

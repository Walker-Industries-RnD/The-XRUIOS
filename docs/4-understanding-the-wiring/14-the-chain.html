The Chain: what connects to what

This page follows the real connections between projects, files and processes. Every arrow was checked against the source. If you want to know what a single file does, use the page for its project; if you want to know what happens next, use this page.

1. Project graph

An arrow means "references". Workers get the same references through src/workers/Directory.Build.props, so no worker .csproj lists them.

Things that are easy to get wrong:

  • SecureLayer references Interpreter, not the other way round. SecureWorkerHost switches to the Aether shell interpreter when XRUIOS_SHELL=aether, and WorkerEvents uses EventJson from the Interpreter.
  • A worker is not a library consumer of the Manager. The two never reference each other; they only meet over the encrypted channel.
  • XRUIOS.Aether does not reference SecureLayer. It compiles six of its files directly, because Godot needs net8.0.
  • The external libraries are DLLs in libs/. SecureLayer uses PariahCybersecurity, EclipseProject, EclipseLCL, SecureStore, NotaryCore and NotaryShared. The Manager adds PermissionHandler (XRUIOS.Permission) and KeeperOfTomes, plus its own copies of the Eclipse, Pariah and Notary DLLs. Workers get EclipseProject, PariahCybersecurity, KeeperOfTomes and Secure Store from Directory.Build.props.

2. Manager startup

Files involved, in order: Program.cs, ManagerHost.cs, SingletonGuard.cs, LoginService.cs, KeyAuthority.cs, PermissionService.cs, ManagerIdentity.cs, SealedFile.cs, NotaryVerifier.cs, AppCatalog.cs, AppRegistry.cs, BrokerRouter.cs, WorkerEventPump.cs, EventHub.cs, AppLauncher.cs, WorkerCatalog.cs, WorkerSupervisor.cs. In SecureLayer: SecureWorkerHost.cs, AuditTrail.cs.

3. Worker startup

A worker's own Program.cs is short. It binds the context and its own data, then calls SecureWorkerHost.Run. The capability file next to it (Capabilities.cs) is what WorkerOcean scans.

4. One call, hop by hop

An app calls AppShell.Broker.InvokeAsync<string>("GetEvents", ...). This is everything that happens, with the file for each hop.

# Where File and method What happens
1 App Apps.Shared/Holes/CalendarPicker.cs A hole builds the argument map.
2 App Apps.Shared/WorkerBroker.cs InvokeAsync Hands the call to the client.
3 App SecureLayer/EclipseSecureClient.cs InvokeAsync Takes the call gate, encrypts the call with the app's session key. A dropped session is re-handshaken once.
4 Broker SecureLayer/SecureWorkerHost.cs PlaguesDiracService.InvokeAsync Finds the session, decrypts, calls the router (the broker has a router set, workers do not).
5 Manager Manager/BrokerRouter.cs RouteAsync Takes the app id from the session identity.
6 Manager Manager/PermissionService.cs CheckAsync App must hold the capability at level 1. If not, write a deny audit entry and refuse.
7 Manager BrokerRouter.cs Find the first worker whose announced capabilities contain the name. Remove __xruios.* arguments from the app, add __xruios.caller.
8 Manager Manager/WorkerSessionPool.cs InvokeAsync Borrow a warm session to that worker (up to 4 per worker).
9 Manager EclipseSecureClient.InvokeRawAsync Encrypts for the worker with the Manager-to-worker session.
10 Worker SecureWorkerHost.cs PlaguesDiracService.InvokeAsync Decrypts, hands to the local WorkerOcean.
11 Worker SecureLayer/WorkerOcean.cs HandleRequestAsync ManagerOnlyGate check, bind arguments by name, run the method, write an audit entry.
12 Worker workers/XRUIOS.Worker.Calendar/Capabilities.cs The [SeaOfDirac] method runs and uses systems/CalendarClass.cs.
13 Worker WorkerOcean.Reply Encrypts the result for the Manager.
14 Manager EclipseSecureClient.InvokeRawAsync Decrypts the result bytes only; it does not deserialize them.
15 Manager BrokerRouter.cs Writes an allow audit entry, encrypts the same bytes for the app.
16 App EclipseSecureClient.InvokeAsync Decrypts and deserializes to the type the app asked for.

Two walls are crossed in that path: the app-to-Manager channel (steps 3 to 4 and 15 to 16), and the Manager-to-worker channel (steps 9 to 10 and 13 to 14). Each channel has its own keys.

5. App enrollment

How an app comes to hold an id, a password and a broker address.

The Manager makes the password again on every start, so it never exists on disk (except in a .creds file when --dev-creds is used on purpose).

6. Events

Each hop keeps its own cursor. If a worker restarts, its new epoch id makes the Manager read from the start of the new log. If the Manager restarts, an app's old cursor is detected as "ahead", and the app is told some events may have been missed.

7. Approval and baselines

Rebuilding a worker changes its files, so it will not start until it is approved again. baseline with no names approves everything found; baseline Calendar approves one.

8. Audit

The first check catches an edited or reordered line. The second catches a log that was cut short, which the chain alone cannot see.

9. Key tree

Separate from this tree, the passwords (PSKs) are plain random bytes: one per worker and one per app, made by the Manager at start and kept in memory.

8 - XRUIOS.Manager

What is it?

If the XRUIOS.Core was the most important, the XRUIOS Manager is by far the most comprehensive part of the system. This page goes through every file in src/XRUIOS.Manager and says what it does. For how the files connect to each other and to the rest of the solution, see 14 - The Chain.

The Manager is one program with a set of command line verbs:

Verb What it does
run [--dev-creds] Unlock, start the broker, launch the workers, and stay up until stopped.
start Same as run, detached in the background.
run-service Same as run, hosted as a Windows Service.
login Create the first account, or unlock and seal the session.
status, stop Check or stop the running Manager.
baseline [name...] Approve worker and app folders as they are now (signs their file trees).
install-app <manifest.json>, uninstall-app <name>, apps Add, remove or list third-party apps.
audit [log] [count] Verify every audit log and print the newest entries of one.
cert add <file>, cert list, cert verify, cert remove <name> The certificate vault (see CertificateVault below).
install, uninstall, install-service, uninstall-service Register or remove autostart.

Starting up and staying alive

Program

The entry point. It prints the banner and sends the verb to ManagerHost (or ServiceHost / AutostartInstaller).

ManagerHost

The orchestration behind every verb. RunAsync goes through these steps in order:

  1. Take the single-instance lock (SingletonGuard). A second Manager exits with code 66.
  2. Harden the process against injection and debuggers.
  3. Unlock: read the sealed session copy of the master key (LoginService). No seal means the Manager stays locked and starts nothing.
  4. Build the trusted core: the permission store, the Manager's signing identity, the audit log, the per-run app credentials, the broker, the event pump, and the enrollment pipe.
  5. Launch the workers, a few at a time. The default is 3 at once because starting all of them together (each a full .NET and web server process) used more memory than a 16 GB machine had. XRUIOS_LAUNCH_PARALLEL changes the batch size.
  6. Every 5 minutes, and once more at shutdown, record each worker's audit head in the Manager's own log.

--dev-creds (or XRUIOS_DEV_CREDS=1) also writes plaintext <app>.creds files into the Public folder so apps started from an IDE can find their credentials. Without it, any left-over .creds files are deleted at start, because a readable password would let any local process act as that app.

SingletonGuard

A global named mutex (Global\XRUIOS.Manager.Singleton). Only one Manager exists per device.

ServiceHost and AutostartInstaller

ServiceHost runs the Manager as a Windows Service (on Linux it just runs normally). AutostartInstaller registers it: a scheduled task at logon (install), a Windows Service at boot (install-service, needs an elevated shell), or a systemd user unit on Linux.

Keys and identity

LoginService

Creates users and unlocks them. A user's master key is 32 random bytes, wrapped with AES-256-GCM under a key from Argon2id over the XRUIOS password (64 MiB, 3 passes, 4 lanes). On Windows a second copy is sealed with DPAPI for the current user, so the Manager can start without a password prompt. On Linux there is no seal yet, so the password is needed each cold start.

KeyAuthority

Holds the master key while unlocked and derives every other key from it with HKDF-SHA256. Each purpose has its own label, so one key never decrypts another's data:

Method Label Protects
DeriveWorkerKey(name) xruios-worker:<name> That worker's data (and, through AuditTrail.KeyFrom, its audit log).
PermissionStoreKey() xruios-permissions The grant store.
IdentityKey() xruios-manager-identity The Manager's signing keypair on disk.
AppRegistryKey() xruios-app-registry The installed-app list.
ManagerAuditKey() xruios-manager-audit The Manager's audit log.

ManagerIdentity

The Manager's long-lived Dilithium keypair. It is created once per user and stored encrypted (SealedFile) under IdentityKey(). Because it is reused, a baseline signed today still verifies tomorrow. Workers only ever receive the public half.

SealedFile

A tiny encrypted file format: AES-256-GCM, laid out as nonce, tag, then ciphertext. Read returns null for a missing file and throws if the file was tampered with. The identity and the installed-app list use it.

XruiosContext

An implementation of the context interface (data path, public path, key). Workers actually receive those three values as environment variables, which XRUIOS.Core binds (see 7 - XRUIOS.Core).

Trusting workers and apps

NotaryVerifier

The Manager's "is this folder the one I approved" check. ApproveAsync Blake3-hashes a folder, signs the tree with the Manager's identity (BaselineSeal), and stores the tree and signature under Baselines. IsCleanAsync re-hashes and compares. A folder with no signed baseline is not trusted on first sight; it stays down until someone runs baseline. Revoke forgets an approval (used by uninstall-app).

WorkerCatalog and WorkerDescriptor

WorkerCatalog is the list of workers, each with its permission group (28 of them). It also finds each worker's built executable, looking in XRUIOS_WORKERS_ROOT first and then in the repo's src/workers build folders. A WorkerDescriptor is a name and an executable path; its folder is the executable's folder, and that folder is what gets hashed.

WorkerSupervisor

Launches a worker only if NotaryVerifier says its folder is clean. It makes the worker's 256-bit PSK, starts the process with its environment (see 5 - XRUIOS.Worker), and waits up to 20 seconds for an announcement whose process id matches. If a worker exits, the supervisor re-checks the folder and restarts it, at most 3 times. StopAll ends them on shutdown.

CertificateVault

A place to keep certificates safely, written for the day WalkerWorks issues them. A certificate goes in, the Manager encrypts it, signs the encrypted copy with its post-quantum identity key, and checks both before trusting it. Until WalkerWorks exists you add certificates yourself.

  • Where. Users/<id>/Certificates: incoming (drop a file here and the Manager seals it at the next start; KeeperOfTomes notices what is new), sealed (the encrypted .sealed copy and its .sig), and ledger.
  • Keys. The files are encrypted under a key derived for the vault only (xruios-certificate-vault), and signed with the Manager's identity key. That identity is stored, so a certificate sealed today still verifies tomorrow. (An earlier version made a new signing key on every run, which meant nothing it sealed could ever be checked again.)
  • Commands. cert add <file> seals and verifies one file (names use letters, digits, ., -, _; up to 1 MB; an existing name must be removed first). cert list and cert verify re-check every sealed certificate (signature valid and decrypts) and show OK or INVALID; verify exits with code 3 if any is invalid. cert remove <name> forgets one.
  • At start. Before the broker opens, the Manager seals anything in incoming, re-checks everything sealed, and writes cert-import or cert-invalid to its audit log. A certificate that no longer verifies is reported, not silently dropped.
  • What it does not do yet. Nothing else in the Manager consumes a trusted certificate. Baselines are still signed by the Manager itself (NotaryVerifier); the vault is where WalkerWorks-issued certificates will wait.

Apps

AppCatalog

The built-in apps: the console sample, the 13 UI apps and the diagnostics harness, each with exactly the capabilities and events it may use. It also finds each app's executable, and holds LegacyGrants (grants an old version made that must now be revoked, for example PocketPal's old Recent).

AppRegistry (and AppManifest, InstalledAppStore)

  • AppManifest is what an app is allowed to be: a name (its id is app:<name>), the executable that may enroll as it, its capabilities, and its events.
  • AppRegistry makes a fresh 256-bit password for every app on every Manager start. It lives only in Manager memory. The broker looks an app's password up by its id.
  • InstalledAppStore is the encrypted list of third-party apps and what each was granted last time, so a capability removed from a manifest is really revoked.

Install a third-party app with a manifest file:

{
  "name": "MyWeather",
  "exe": "C:\\Apps\\MyWeather\\MyWeather.exe",
  "capabilities": [ "Current" ],
  "events": [ "WeatherUpdated" ]
}

Run XRUIOS.Manager install-app manifest.json, then restart the Manager. Names may use letters, digits, ., - and _, and may not reuse a built-in name.

AppLauncher (the "app identifier")

Apps can be their own executables. An app asks the Manager for credentials over a local pipe (xruios-manager-control). The Manager does not trust what the app says about itself. For one request at a time, it:

  1. Checks the app name is registered.
  2. Finds the real calling process from the pipe, and reads that process's executable path.
  3. Checks the process runs from the app's registered path.
  4. Checks the app's install folder against its approved baseline (NotaryVerifier).
  5. Only then returns the app id, its password and the broker address.

The pipe also accepts spawn <app>, which has the Manager start a registered app with its credentials in the environment (XRUIOS_APP_ID, XRUIOS_APP_PSK, XRUIOS_BROKER_ADDR). Every enroll and spawn decision is written to the audit log.

Handling calls

PermissionService

A thin wrapper over the external XRUIOS.Permission library. It stores {app id -> {capability -> level}} in an encrypted file under the permission key. A grant is level 1, a revoke sets level 0, and a check requires level 1, so anything never granted is denied.

Why it remembers answers. The store itself rate-limits every app to 100 checks per minute. Every call is a check, so an app calling faster than about once every 0.6 seconds (a slider drag, a window that polls) used to run out, and the failure came back as an opaque "Exception was thrown by handler". PermissionService now remembers each (app, capability) answer for 15 seconds, and a grant or revoke clears the memory. BrokerRouter also turns any remaining store failure into a plain message ("could not be completed, try again shortly") and a deny audit entry.

BrokerRouter

The core that talks to applications. For each call it:

  1. Answers Events.Poll itself, filtered by the Events.<Name> grants of the app.
  2. Checks the app's grant. Denied calls are written to the audit log and refused.
  3. Finds the worker whose announced capabilities include the name (the first match).
  4. Removes any __xruios.* argument the app sent, adds the real caller as __xruios.caller, and relays the call to the worker over a pooled session.
  5. Re-encrypts the worker's exact result bytes onto the app's channel.

A worker's error comes back as an ordinary failed response with the worker's own message, instead of an opaque handler error. The app never touches the worker, and the worker never sees the app.

WorkerSessionPool

Keeps warm Eclipse sessions to each worker so the broker does not repeat the handshake (enroll, Kyber, Dilithium sign and verify) on every call. Because Eclipse numbers messages, one session carries one call at a time, so each worker gets a pool of up to 4. If the worker moved to a new address or a session expired, the pool reconnects and retries once. It does not retry when the worker itself reported a failure, so a call with a side effect is never run twice.

EventHub and WorkerEventPump

WorkerEventPump keeps one long-polling session per worker (separate from the call pool, so a 20 second poll never blocks a real call) and copies each worker's events into EventHub. The hub is one ordered log of the last 2048 events with the Manager's own sequence numbers, so an app's cursor survives any worker restarting. Apps read it through Events.Poll.

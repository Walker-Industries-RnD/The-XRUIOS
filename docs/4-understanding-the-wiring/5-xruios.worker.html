5 - XRUIOS.Worker

What is it?

The XRUIOS workers are the isolated OS-level programs the XRUIOS.Manager talks to. Each one is its own executable (XRUIOS.Worker.<Class>), compiles only its own system class, and receives its own password and its own encryption key from the Manager. Everything below is what a worker actually does when SecureWorkerHost.Run starts it, in order.

What a worker does at startup

  1. Refuses to run without the Manager. A worker only starts when the Manager launched it (XRUIOS_MANAGER_MANAGED=1). Started by hand it prints a message and exits with code 2. For debugging one worker alone, set XRUIOS_DEV_STANDALONE=1; it then makes a throwaway secret that nobody holds, so nothing can call it.
  2. Hardens the process. It blocks DLL injection and starts a debugger watchdog. If a debugger attaches later, the worker wipes its PSK and exits with code 66.
  3. Reads what the Manager handed it through environment variables.
Variable What it is
XRUIOS_WORKER_PSK The worker's 256-bit access password. Only the Manager has the other copy.
XRUIOS_MANAGER_PUBKEY The Manager's PUBLIC signing key. The private half never leaves the Manager.
XRUIOS_DATA_PATH, XRUIOS_PUBLIC_PATH Where this worker's data lives.
XRUIOS_WORKER_KEY This worker's own encryption key, derived from the master key. It is never given another worker's key.
XRUIOS_BASELINE, XRUIOS_BASELINE_SIG Path of the file tree the Manager approved for this worker, and the Manager's signature over it.
  1. Checks its own folder against the Manager's signed baseline. NotaryGuard verifies the Manager's signature over the tree, then Blake3-hashes every file in the worker's folder and compares. A bad signature, or any modified, missing or added file, exits with code 44. The same check repeats every 30 seconds while the worker runs. The Manager sees the exit, re-checks the folder, and restarts the worker (at most 3 times).
  2. Makes its Kyber keys, builds its capability table, opens its audit log. WorkerOcean scans the worker's assembly for [SeaOfDirac] methods.
  3. Listens on a loopback port that the OS picks (or a Unix socket on Linux), then writes its address, capabilities, public key and process id to the SecureStore under WorkerAnnouncement.StoreKey(<name>). The Manager waits for an announcement whose process id matches the process it just launched.

What a worker does with each call

  • It only serves the Manager. The handshake needs the worker's PSK, and enrollment needs a valid Manager signature over the caller's id. A caller that somehow had the PSK but not the Manager's private key is refused at enrollment, and the worker's ManagerOnlyGate refuses calls on any session the Manager did not open.
  • It exposes only its own capabilities. Anything else returns "Capability not found".
  • It never decides who an app is. The Manager already checked the app's grant. It stamps the calling app's id into the call as __xruios.caller, and the worker reads it through WorkerCall.CallerAppId when it wants to record who asked.
  • It records every call. Each call, success or failure, is one entry in the worker's audit log (see 9 - XRUIOS.SecureLayer for the log format). The log is tamper-evident, not secret: a worker can write it and the Manager can verify it, but anyone who edits a line breaks the chain.
  • It publishes events. WorkerEvents.Publish(name, payload) adds to a small in-memory log that the Manager long-polls.

What is not true

Earlier versions of this page listed behaviours the code does not have. For clarity: there is no Shamir secret splitting (each worker's key is an HKDF derivation of the master), no heartbeat from worker to Manager, no revocation list, and no OS container or sandbox around a worker. A worker is a normal process. Its protection is the three walls in 1 - The Model, not process confinement.

Why there is no "allow all" gate any more

Workers used to be started with AllowAllPermissionGate, with the explanation that the Manager checks permissions. That was true but weak: it relied on nobody reaching the worker. The default gate is now ManagerOnlyGate, which serves a call only on a session whose enrollment carried the Manager's signature. AllowAllPermissionGate still exists but is marked [Obsolete], and no worker uses it.

Per-app permission decisions still happen at the Manager's broker, not in the worker. Reaching a worker now needs all of:

  1. The worker's ephemeral address (published only in the user's SecureStore).
  2. The worker's 256-bit PSK (in Manager memory and the worker's environment).
  3. The Manager's private signing key, to sign the enrollment.
  4. A worker folder that still matches the Manager-signed baseline.

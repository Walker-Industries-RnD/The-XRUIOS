Every File and How They Connect

This page walks the whole tree, folder by folder, then the Yuuko Protocol repo, then shows where the two meet. Read 16 - The Big Map first for the picture; this page is the legend that goes with it.

(I KNOW i'm gonna forget how the XRUIOS works and I hate myself for it, so this is what this is for)

Two repos are covered:

  • The XRUIOS (GitHub/The XRUIOS): the trusted core, 28 workers, the apps, the tests.
  • Yuuko Protocol (GitHub/YuukoProtocol): pub/sub messaging, encrypted peer sessions, and the Bindings that make file locations portable between devices.

1. The shape in one paragraph

An app asks the Manager for something. The Manager checks the app's permission, finds the worker that announced that capability, and relays the call over an encrypted channel. The worker runs the real logic in a class from src/systems, stores its data encrypted, and answers. Workers are only started if their folder matches a signature the Manager made. Yuuko Protocol is a separate library for talking between devices; today it shares code and the Eclipse crypto library with the XRUIOS, but no XRUIOS process calls it yet.

4. src/ projects, in the order data flows

4.1 Shared contracts

  • XRUIOS.Contracts: IXruiosContext.cs (the paths and key a worker is handed) and PermissionGroup.cs (the 7 permission groups).
  • XRUIOS.Core: XRUIOS.cs, the static holder each worker binds at start (data path, public path, its own key). An unbound context throws.

4.2 The logic

  • src/systems/ (*Class.cs, Songs.cs, Processes.cs and so on): the real work, one file per system class: Alarm, Calendar, Clipboard, Identity, Note, Songs, Theme, Timer, Volume and the rest. Each has a CRUD set plus an initializer and stores its data encrypted under Data/<Class>.
  • XRUIOS.Systems: a project of its own beside the logic folder (see 3 - XRUIOS.Systems for what the classes do).
  • XRUIOS.Interfaces/Functions/: the records and types those classes use, such as SongOverview. Apps may reference these without referencing any logic. Songs.cs also holds the audio tag capability table, unused for now.

4.3 The trusted core: XRUIOS.SecureLayer (runs inside every worker and the Manager's broker)

File Job
SecureWorkerHost.cs Starts a worker (or the Manager's broker): opens the Eclipse server, announces the address, reconnects dropped sessions
WorkerOcean.cs Finds methods tagged [SeaOfDirac], binds them by name, runs one call, audits it
Permissions.cs ManagerOnlyGate: only sessions carrying the Manager's signature may call a worker
NotaryGuard.cs The worker checks its own folder every 30 s; a mismatch exits with code 44
BaselineSeal.cs Hashes a folder one file at a time, signs and verifies the result (Dilithium)
AuditTrail.cs Chained HMAC log; also reports its newest entry so the Manager can anchor it
EclipseSecureClient.cs The client half: handshake, calls one at a time, re-handshakes if the session drops
XruiosEnrollment.cs, AppProvisioning.cs How an app asks for its per-run password over the pipe xruios-manager-control
XruiosEventStream.cs, XruiosEvents.cs Long polling for events; WorkerEvents.Publish for workers
WorkerAnnouncement.cs, Utils.cs The address file in the TEMP SecureStore folder (owner-only)
PqcGate.cs Lets only one crypto operation run at a time (the native library needs it)

4.4 The trusted core: XRUIOS.Manager (one per device)

File Job
Program.cs, ManagerHost.cs The command line verbs: run, start, stop, status, login, baseline, install-app, uninstall-app, apps, audit, cert, install, uninstall
LoginService.cs, KeyAuthority.cs Argon2id login, then one key per purpose from the master key (permissions, identity, apps, certificates, audit, each worker)
ManagerIdentity.cs, SealedFile.cs The Manager's own signing keys, stored sealed
AppCatalog.cs, AppRegistry.cs, AppLauncher.cs Which apps exist, a fresh password for each run, and the enrollment pipe
PermissionService.cs Grants and checks, with a 15 s memory of answers
BrokerRouter.cs, WorkerSessionPool.cs Check, relay through one of 4 warm sessions, audit
EventHub.cs, WorkerEventPump.cs Collects worker events and hands them to the apps allowed to see them
WorkerCatalog.cs, WorkerDescriptor.cs, WorkerSupervisor.cs The list of 28 workers, finding their executables, launching 3 at a time, restarting
NotaryVerifier.cs Approves a folder (baseline) and checks it before any launch
CertificateVault.cs Sealed certificates, cert add/list/verify/remove
AutostartInstaller.cs, ServiceHost.cs, SingletonGuard.cs Logon task, Windows service, one Manager at a time
XruiosContext.cs A context class in the Manager project; nothing calls it at the moment

4.5 What touches the machine: XRUIOS.Interpreter

XruiosInterpreter.cs picks a backend. Windows/* and Linux/* call the operating system (audio, power, clipboard...). AetherShellInterpreter.cs instead sends events for a game engine to draw. DeveloperInterpreters.cs holds event names and Dispatch. XRUIOS.Interpreter.Probe is a small program that exercises it.

4.6 Workers: src/workers/XRUIOS.Worker.*

28 folders, one per system class: Alarm, App, AreaManager, Assistant, Calendar, Chrono, Clipboard, Creator, DataManager, DeviceManager, ExperimentalVolume, Geo, Identity, MediaAlbum, MediaTagger, MusicPlayer, Note, Notification, Processes, RecentlyRecorded, Songs, SoundEQ, Stopwatch, SystemInfo, Theme, Timer, Volume, WorldEvents. Each has the same two files:

  • Program.cs: bind the context, initialize the class, hand control to SecureWorkerHost.
  • Capabilities.cs: the [SeaOfDirac] methods, the only way in. To add a capability you edit only this file.

src/workers/Directory.Build.props gives every worker workstation garbage collection, which keeps each worker between about 16 and 29 MB.

4.7 Apps: src/apps and the helper projects

  • XRUIOS.Apps.Shared: what apps build on. WorkerBroker.cs finds credentials, AppShell.cs connects once, Holes/*.cs are one-line wrappers per capability, Holes/EventFeed.cs delivers live updates, AssistantProvider.cs plugs in your own AI.
  • XRUIOS.App.*: 13 apps (AppLauncher, Calendar, Clipboard, Gallery, Keyboard, Notifications, PocketPal, Power, ThemeEditor, Time, VolumeManager, Weather, WorldEvents).
  • XRUIOS.SampleApp: the smallest app that talks to the Manager.
  • XRUIOS.Diagnostics: asks every worker a health question (33 probes).
  • XRUIOS.Aether: AetherShell.cs, the library a game engine uses to act as a XRUIOS shell.
  • XRUIOS.AetherModTest: shows an engine mod being treated as an app for permissions.

4.8 Tests: XRUIOS.E2E

Program.cs holds 20 sections (regression, burst, clock, calendars, albums, enrollment, assistant, events, alarm, timer, recent, processes, notes, areas, datamanager, creators, mediatags, identity, songs, musicplayer). run-e2e.ps1 builds a throwaway data root, creates an account, approves everything, starts the Manager, runs the sections and the diagnostics harness, then prints a memory table. e2e.harness.manifest.json grants the test app every capability. Last result: 180 passed, 0 failed.

5. The Yuuko Protocol repo

Layout: YuukoProtocol/YuukoProtocol/ is the library, YuukoProtocol/YuukoSandbox/ is a test and benchmark program, docs/ is the exported wiki, ZenohNative.targets fetches the native Zenoh library.

5.1 Networking/ (the pub/sub and secure sessions)

File Job
YuukoPacket.cs The unit of data: Name, Type, Data bytes, Flags (tombstone = delete, ephemeral = do not keep). JSON on the wire
IYuukoApi.cs The interface: Publish, Request (stored packets), Subscribe, Unsubscribe, Tombstone. Also LocalBroker, an in-process version used for tests
ZenohBroker.cs The real network transport over Zenoh: peers find each other on the LAN or connect through a router; optional TLS under the encryption
YuukoHandshake.cs Builds an encrypted session between two peers: Hello, Challenge, Response, Accept or Reject, using Kyber-1024 and the Eclipse crypto; each session has 8 independent lanes
EclipseBroker.cs Sits on any transport: a provider Serves packets, a requester RequestAsync(provider, topic) and gets them decrypted; all traffic is ciphertext
YuukoExtensions.cs Small helpers such as PublishJsonAsync

How a request travels: the requester handshakes with the provider over topic yuuko/handshake, both derive the same lane keys, then the request goes over yuuko/eclipse/data encrypted on one lane, and the answer comes back on the same lane. The transport underneath (LocalBroker or Zenoh) only ever sees ciphertext after the handshake.

5.2 Backend/ (Yuuko Bindings: files that follow you between devices)

File Job
Bindings.cs DirectoryManager: remembers a folder by an ID made from device name plus path, and resolves it to a real folder on this device; DirectoryBinding, DirectoryRef, DirectoryResolution
Media.cs Keeps an encrypted list of folders per data type (GenericBank) and finds a file inside a bound folder
DirectoryRecord.cs, FileRecord.cs, ResolvedMedia.cs, Handle.cs The records those classes return
App.cs The app description records (overview, events, parameters, per-OS builds)

5.3 YuukoSandbox

MainTest.cs is an interactive demo (it waits for a key). Benchmark.cs (dotnet run --project YuukoSandbox -- bench) measures handshake and request speed. YuukoTopics.cs holds the canonical topic names (yuuko/xruios/config, yuuko/xruios/events, yuuko/xruios/sync and others).

6. Where the two meet

  1. Shared code, copied. src/YuukoProtocol.XRUIOS.Interfaces holds the same Backend files as the Yuuko repo (identical now, except that the Yuuko repo's App.cs has one extra empty method, CreateSign). System classes that store media folders, such as Songs and MediaTagger, use it.
  2. Shared crypto. Both sides use the Eclipse DLLs and Pariah, but with separate sessions: the XRUIOS channel is Manager-to-worker on one device; Yuuko's is device-to-device.
  3. No live link. No XRUIOS process publishes to or subscribes on a Yuuko topic. A Yuuko app that does so would be installed like any other XRUIOS app (manifest, per-run password, granted capabilities), read local events, publish them on yuuko/xruios/events, and apply incoming packets by calling XRUIOS capabilities.
